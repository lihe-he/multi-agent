# Workflow 协议（alpha.24）

本文说明 `0.2.0-alpha.24` 的版本化流程定义、候选发布、节点运行和导出边界。该增量提供本地 API 模型路由的基础 DAG 路径；M0–M3 的完整产品退出条件及三端发行验收仍未完成。

## 定义与版本

Workflow 使用版本 `1` 的 JSON DSL，仅接受 `dslVersion`、根输入、`maxParallel` 与 `nodes`。输入根来源限定为 `goal`、`contract`、`context` 和 `baseline`；节点数为 1 至 64，并声明类型、职责版本、依赖、输入输出、范围、权限、调用上限、时限、验收和终止条件。流程校验会拒绝未知字段、循环依赖、无祖先提供者的输入、重复逻辑产物和不支持的权限组合。

每个版本固定其规范 DSL 摘要、Agent 职责快照与项目归属。编辑产生新的版本，乐观并发检查防止覆盖；复制产生新身份，回退也作为新版本保存。JSON 导入/导出保留实际定义和摘要。项目只能读取本项目及全局定义。

任务创建时通过流程选择固定版本和摘要。对非根模型路由需在任务操作前明确批准；创建任务时还要保留该项批准。运行前会复核路由、根锁定、流程摘要、定义版本、任务授权和工作目录绑定。

## 路由检查与发送确认

`POST /api/workflows/readiness` 在任务创建前接收 `projectId`、`routeId`、可选的 `locks`，以及仅含 `definitionId`、正整数 `version` 和 `digest` 的 `selection`。`POST /api/tasks/{id}/workflow-readiness` 接收同样的三个流程版本字段，使用该任务已经固定的项目、根路由快照和锁定。两种检查返回根路由、节点接收路由、声明输入及其中的根输入、额外路由和阻塞原因；返回路由身份包含版本、引擎、供应商、模型和 API 地址，不返回 API 密钥、任务目标、上下文内容或节点产物。

检查和最终选择使用同一路由解析逻辑：空职责路由或显式引用根路由的节点使用根快照，其余节点读取明确的额外路由版本；职责须仍启用且属于当前项目或全局。原生 CLI、停用或缺失路由及不符合根锁定的组合有明确阻塞。检查只读取本地记录，不运行探针、模型或工具，不产生授权和任务快照；无阻塞也不证明凭据、实际端点兼容性或最终权限交集已经验证。创建或替换任务流程时仍须执行完整门禁。

新的流程选择使用以下结构，`allowedRouteVersions` 必须与实际额外接收者一一对应，不能多报、少报或使用过期版本：

```json
{
  "definitionId": "published-workflow",
  "version": 2,
  "digest": "the-selected-version-digest",
  "rootRouteVersion": 3,
  "allowedRouteVersions": {
    "explicit-alternate-route": 5
  }
}
```

任务创建时将该对象作为 `workflow`；已有任务的 `/workflow-selection` 或 `/workflow-restart` 将其作为 `selection`，并继续提交接口原有的任务版本、原快照、运行代次及重新开始依据。根路由版本以实际使用的根快照为准：新任务检查当前路由；已有任务继续使用原来固定的根路由，不能因同一身份后来编辑为新端点便静默改发。额外路由在最终选择时按明确版本核对。编辑、停用或刷新路由后，客户端应重新检查并确认；旧检查结果不授权新版本。探针结束时若配置版本已变，拒绝把旧结果覆盖到新配置。

为兼容旧客户端，没有额外接收者的同根路由选择仍接受原有字段及省略的新字段。旧 `allowedRouteIds` 字段不授予任何额外发送权限；只有身份列表的跨路由选择被拒绝。已经保存的任务快照继续代表其原路由和原批准，不按新字段推测补写历史授权。

## 执行与恢复

流程运行建立新的持久代次和基线副本。仅当声明依赖成功的节点进入 DAG 调度；并行度同时受 DSL 和任务协作上限约束。节点在独立 Worker 现场准备祖先输入，通过实际模型请求和逐轮根预算，保存脱敏证据、版本和原 Worker 回执。

节点的自动提示交接只投影其 `inputs` 声明：`goal` 提供根目标，`contract` 提供根完成约定，`context` 提供固定项目上下文中的普通记忆条目，`baseline` 提供基线版本；逻辑产物引用保留声明祖先的尝试、AgentRun、证据和成果版本。未声明的根目标、完成约定或项目记忆不会作为隐含字段再次追加到该节点提示。根完成约定仍控制实际工具权限、必要验证和独立审查，不因某节点未声明 `contract` 而取消。

每个节点仍接收固定的节点目标、职责说明、节点验收和终止条件、实际权限，以及适用的固定仓库规则。仓库规则是平台从 `AGENTS.md` 建立的专用 `project-rules` 条目，单独提供来源、版本和内容，不提供宿主绝对 `sourcePath`；即使未声明 `context` 也会提供，声明上下文时不重复该规则。普通 `RULE` 类型项目记忆不是这项强制规则，仍需声明 `context` 才会自动注入。路由确认应同时披露这项共同资料和相应节点声明的可选资料。

声明输入控制的是平台主动组装的提示资料，不是独立的数据隔离沙箱。被授权的文件读取和检索仍按实际权限交集执行，祖先文件准备仍按既有范围处理；允许的团队消息、副 Agent 和声明祖先输出也可能携带此前获得的资料。节点输出保留原来源，不因转述成为更高权限或更强证据。本次交接调整不移除已有文件、团队或固定 MCP 权限，也不新增原生 CLI 或任务限定 MCP 桥接。

写入节点的变更经过版本核对后才整合到根现场。流程只是阶段编排，不能跳过根任务既有的必要验证、独立审查或人工验收。成功节点通过原输入、请求、证据、Worker 租约、现场版本和摘要复核后才能在同一流程恢复时复用；新的尝试沿用根预算并获得新的尝试编号。

暂停或取消会停止后续节点。若原 Worker 调用已返回，根停止已确认，且能持久核对未发出模型请求、零请求消耗和无未知效果，该等待可记录已确认取消后恢复。已经发出的模型请求、外部工具或丢失的执行回执不据异常类型推断结果；保留 `UNKNOWN` 并禁止自动重放或续跑。

## 内置模板升级与历史

在职责及发布条件满足时，仍启用且未经编辑、内容与历史模板吻合的三种内置 v1 会发布新的 v2，显式为实现节点补充 `goal` 和 `contract` 输入。原 v1、其职责快照、摘要和已有任务选择保持；新建库同样先保存 v1 再发布 v2，重复初始化不继续产生版本。已停用、已编辑或不符合原模板的定义不自动覆盖。

新节点输入准备操作、尝试和结果证据带有 `promptInputProjectionVersion=1`；输入准备另保存 `projectRuleSources`。这些事实随原回执和证据参与既有完成证明。旧记录没有该字段时保留原状，不能据当前代码为其补造投影已经生效的证明；经既有完整性门禁复用的旧成功节点，仍代表当时真实请求产生的结果，输出可能包含旧实现曾主动提供的资料。选择旧 DSL 不会恢复旧的隐含提示拼接；需要根目标或完成约定的节点应编辑发布明确输入的新版本，已有任务升级仍需用户另行选择和授权。

## 候选生成与导出

用户可以基于现有任务输入请求只读候选。每次生成固定原请求编号、定义版本、输入摘要、调用限制和实际任务来源。模型只能调查并返回 JSON 流程草案，平台按同一 DSL、项目、权限及职责版本校验；解析或校验失败仍保留原模型证据。

候选不会自动成为任务流程或已发布版本。用户可以查看原证据和摘要、修改名称及 DSL、重新校验，再按原来源摘要发布。发布采用版本冲突检查；相同原请求和发布参数的重试不会生成第二个版本。使用候选需要另行对发布版本做任务选择与授权确认。

任务 ZIP 含 `workflow-runs.json`、`workflow-node-attempts.json`、`workflow-proposals.json` 与 `workflow-generations.json`。归档保留流程运行、节点尝试、生成请求和候选之间的来源引用；任务导出不是数据库或完整配置备份。

## API

- `GET/POST /api/workflows`：列表与新版本发布。
- `POST /api/workflows/validate`、`/api/workflows/import`：校验、导入。
- `POST /api/workflows/readiness`：创建任务前检查固定流程版本的路由、声明输入和阻塞原因。
- `GET /api/workflows/{id}/versions[/{version}]`、`/{version}/export`、`/rollback`：历史、单版本和版本回退。
- `POST /api/tasks/{id}/workflow-readiness`：按原任务固定根路由和锁定进行同类只读检查。
- `POST /api/tasks/{id}/workflow-selection`、`/workflow-restart`：固定新选择或明确建立新代次。
- `GET /api/tasks/{id}/workflow-runs`、`/workflow-runs/{runId}/attempts`：有界分页读取运行与节点记录。
- `POST/GET /api/tasks/{id}/workflow-generations`、`GET /workflow-proposals`：提交只读生成和读取来源历史。
- `GET /api/tasks/{id}/workflow-proposals/{proposalId}`、`POST /workflow-proposals/{proposalId}/publish`：查看候选并按摘要明确发布。

上述路由均遵循 API 原有认证、任务项目归属、原请求来源及并发控制。该 API/W​​orker 协议在 alpha.24 不改变版本号 `1`。
