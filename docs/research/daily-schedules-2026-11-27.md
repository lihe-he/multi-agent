# 每日持久调度设计研究

研究日期：2026-11-27。范围是 F21 的本机每日触发、时区规则、漏跑审计、版本化修改和重启恢复。产品退出条件仍以[计划书](../多Agent智能研发工作台计划书.md)为准，实现接口见[持久每日调度契约](../schedule-contract.md)。

## 开源依据与取舍

本仓库已在[持久派发队列研究](./dispatch-queue-2026-11-08.md)固定并审阅 [db-scheduler](https://github.com/kagkarlsson/db-scheduler) Apache-2.0 提交 `ff5e13176a1849d153339664216a616bbe515063`，包括 `JdbcTaskRepository` 的唯一领取约束、`TransactionManager` 的多变更事务边界，以及重试和失败处理职责分离。当前每日调度复用这些设计原则，但结合现有 SQLite owner 和任务实体落库，不引入额外数据库或第三方调度依赖；不会将上游调度器的租约、集群及重试能力归称为本项目已有能力。

每天以计划和本地日期构成幂等键，使用 SQLite 唯一索引阻止同日重复 occurrence；occurrence 创建后先持久化，再通过任务实体唯一关联来恢复或完成任务创建。配置每次变更追加 revision，并以生效区间界定其适用日期，使时间或时区调整不会改写旧日历史。扫描游标随 revision 持久保存，每次限定扫描页数并向前推进。

时间规则明确选择：IANA zone 与严格 `HH:mm`；春季不存在的本地时刻在 DST 转换后记录跳过；秋季重复时刻取首个 offset；超过预定时间五分钟的 occurrence 记为 `MISSED` 且不补跑。核心启动先恢复已持久化的 `PENDING`，包括定义后来停用的情形。处理失败转为可见的 `NEEDS_ATTENTION`，而不是无限期阻塞待处理队列。

## 验证与限制

测试采用可注入固定时钟和真实临时 SQLite，覆盖日期重复、独立任务/session、MISSED、并发唯一插入、revision 的乐观并发更新、停用后 PENDING 恢复、超过 100 日期的游标推进、DST 缺口/重叠、同日修改不产生第二次触发、旧版本回填，以及失败项不会饿死后续记录。最终运行结果应在本轮 QA 回执中记录，单元测试不替代 API 级端到端和发行物验收。

目前没有跨机器 leader election、多核心 owner 的协调/租约、分布式锁、并发调度集群、计划 UI、恢复/备份格式扩展或持续负载验收。未通过这些额外证据之前，本实现只声明当前本机核心的持久每日调度边界，不声明远程或多副本调度。
