## 1. 审查结论

当前项目已经在源码和进程上分出 React 前端、Spring Boot 核心和 Electron 客户端；前端通过 HTTP 调用核心，不是直接从界面调用 Java 类。这是可保留的基础。

但“前后端可独立部署、独立升级、桌面/浏览器/手机共用服务”尚未完成。当前生命周期和权限依然围绕同一台电脑、单用户、Electron 自动管理 Java 进程设计。仅重命名目录或放宽 CORS 不能完成分离。

建议保留 Java 21 + Spring Boot、React + TypeScript 和 Electron。先以一个模块清晰的 Java 后端承载业务，另建有明确协议的本机执行节点；避免为了分离而立即引入大量微服务。Electron 是可选桌面客户端，浏览器和手机使用同一套业务 API。

  modules/project/         项目、分支、工作区、差异与采纳
  modules/orchestration/   Agent、团队、工作流、检查点与任务租约
  modules/policy/          权限模式、审批、设备授权和预算
  modules/integration/     模型、MCP、技能与 IM 适配器
  modules/observability/   活动、请求追踪、用量、检索与调度

contracts/                 OpenAPI、事件协议、执行节点协议与生成客户端

以上是职责划分，不要求立即移动所有文件。可先在原目录抽取接口、补上协议和部署入口，再做目录迁移，减少无业务收益的大规模改名。

后端应区分以下核心对象：Workspace、Project、ExecutionNode、RepositoryBinding、Worktree、Session、Message、AgentDefinition、AgentRun、Team、WorkflowDefinition/Version、WorkflowRun、ApprovalRequest、ToolOperation、Artifact、ModelRequest、UsageEntry、Schedule、IntegrationBinding。所有业务对象使用稳定 ID 和版本；绝对路径属于节点上的仓库绑定，不作为跨设备通用 ID。

## 4. 三种使用方式，共用业务接口

### 本机桌面

Electron 可启动本机 Java 服务和本机执行节点，或连接已经运行的服务。用户仍可在离线可用范围内查看本地任务、使用本地模型。桌面只处理窗口、托盘、系统授权、浏览器预览和本机交互桥接；任务调度与审批结论由后端保存。

### 独立 Web + API

Web 静态资源单独构建，放在 Nginx 等静态站点服务；Spring Boot 作为独立后台服务运行。推荐以同一个 HTTPS 网关暴露 `/` 与 `/api/v1`，前后端仍是独立构建和部署的产物。需要不同域名时，使用部署中列举的允许来源和正式会话机制，不允许任意来源携带管理凭据。

本机执行节点主动连接已配对的后端，运行获授权的项目操作。服务部署在哪里，不改变用户本地仓库的执行归属。前端关闭、移动端熄屏、WebSocket 断开都不应使后台任务丢失。

### 手机 App、H5 与 IM

这些客户端只发目标、查看事件/成果和审批，不在手机执行原电脑上的命令。设备先配对，绑定用户与可访问项目；允许撤销设备、限制权限和过期会话。IM 消息经后端连接器映射为已有身份及项目范围，不能因为知道群 ID 或任务 ID 就取得执行权限。

无需为了移动端控制把本机 Java 管理端口暴露给公网。可通过受认证的后台服务或用户主动配置的私有网络连接本机执行节点；穿透通道是部署能力，不是跳过认证的捷径。

## 5. 接口与权限边界

- REST 负责配置、查询、命令与人工决策；SSE 负责可重放活动事件；WebSocket 负责终端输入、低延迟状态和必要的桌面交互流。协议版本独立于前端安装版本。
- OpenAPI 定义 DTO、枚举、分页、错误码和版本冲突；前端生成类型客户端。每个请求携带工作空间上下文，服务端验证项目权限，不相信客户端传入的 scope。
- 执行节点领取带期限与操作编号的任务租约，回报能力、平台、允许目录、运行器和进程状态。断线后保留未知状态，重连核对操作账本后恢复，不能自动重复副作用。
- 危险操作审批绑定任务、工具、完整参数摘要、目标版本、有效期与单次决策编号。AI 反问和用户审批分别建模。移动端或 IM 审批与桌面审批使用同一个后端事务，避免重复批准。
- 五档权限是策略预设，建议为：只读分析、逐次询问、授权范围自动编辑、授权工作区自动执行、可信工作区跳过询问。具体名称可调整；五档均保留用户/项目/设备边界、根预算、外部副作用和审计规则。“跳过询问”不授予原先没有的项目或设备权限。
- 第三方技能、网页、模型和 MCP 返回内容只作为数据，不能自动修改权限、路由、预算或审批状态。职责模板与动态 workflow 生成物也必须经过同一个验证器。
- 模型官方登录与 API Key 接入是不同凭据类型。只有供应商正式支持并允许的 OAuth/CLI 登录能力才显示为可用；不把网页 Cookie 提取或未经支持的接口当作必然可实现的官方登录。
- 预览浏览器运行在独立进程/会话分区。预览页面可保留自己的登录态和 Cookie，但不能得到平台 API 管理凭据、任意 preload 能力或其他项目的 Cookie。端口、项目、会话与代理 URL 明确绑定。

## 7. 前后端分离的验收标准

1. 只安装 Java 21 和后端产物即可启动 API，不依赖 Electron、Web dist 或 npm。健康检查与服务优雅停止可复现。
2. 只构建 Web 即可发布静态站点；不同部署环境通过运行时配置切换 API，不重编译凭据、不把密钥放入静态产物。
3. 浏览器无 `window.workbench` 时，项目/会话/团队/任务/审批/成果等业务流程可正常运行；本机专属能力明确呈现为需要已配对执行节点。
4. Electron 连接独立服务后退出，后台任务继续；重新打开或手机接入可按游标恢复活动，不重复执行工具。
5. 两个不同设备上的同名路径/仓库能够以节点和项目ID区分，不发生跨机路径混用。
6. 用户、项目、执行节点和工具授权在后端强制；更换客户端或伪造 projectId 不扩大权限。审批绑定版本，过期/撤销/重复审批不能执行。
7. 执行节点断线或重启可核对租约和账本；无回执操作保持未知，需核对后续跑；根取消和预算跨所有后代生效。
8. 独立部署提供迁移、完整备份恢复和兼容版本说明；SQLite 单机部署与 PostgreSQL 集中部署各有实际测试，不靠配置项存在宣称支持。
9. 21项功能分别有完成/部分/待实现/不支持原因与具体证据，既有“绿色CI”不能代替手机、IM、系统桌面或供应商真实验证。

## 8. 迁移顺序

第一步先保存现有开发现场、修复暂停留下的未完成构建，并将前后端运行入口、配置、API契约和鉴权模式分开。保留 0.1 已验证的任务、证据、未知状态和验收门禁。

第二步建立 Session、AgentRun、Team 与执行节点协议，完成浏览器可独立使用的多会话、终端、搜索、差异和活动面板。把本机 Git/CLI/命令能力放到 Worker 接口后，逐步启用远程节点；先不同时改写全部业务存储。

第三步在统一策略与账本上补动态 SubAgent、Teams、Workflow、五档权限、MCP和技能。原始三模式继续作为 workflow 模板存在；不能用固定角色阶段冒充动态协作完成。

第四步接入模型账号/图像、预览浏览器、六主题、定时与用量，并打通移动配对和 IM。各集成独立记录来源、官方能力、凭据方式和平台限制。

第五步补齐三端 Computer Use、桌面宠物、完整备份、长期运行和端到端兼容性验收。此顺序安排开发依赖，不从范围中删除或无限期隐藏任何截图要求。
