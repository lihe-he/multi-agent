# 多 Agent 智能研发工作台计划书

版本：1.1  
更新日期：2026 年 11 月 5 日  
面向读者：产品负责人、架构师、实现工程师和测试人员  
文档性质：产品与技术规划基线，功能按里程碑交付；本文中的策略、默认值和效率指标属于设计目标，不代表已经实现或测得的结果。

本版合并八项完善和两项后续扩展，保留十九章结构，验收场景扩展为 T01—T36。修订与章节、实施阶段的对应关系见第 19.3 节。

## 1 产品目标与已确定的方向

工作台面向开发者，在本地持续理解项目，组织多个 Agent 协作完成研发任务。用户提出目标后，平台先分析需求、已有实现和验收条件，再选择协作方式、模型和工具。执行过程中共享必要信息、保存现场、处理故障；交付前完成验证和独立审查，由用户最终验收。

产品价值集中在四件事：减少重复解释与探索，缩短从需求到验收的时间，降低人工协调和返工负担，并使研发成果能够追溯、恢复和交接。

### 1.1 已确定的产品选择

| 项目 | 规划选择 |
| --- | --- |
| 目标用户 | 开发者，先做好个人及本地研发使用 |
| 产品形态 | Windows、macOS、Linux 桌面工作台 |
| 技术方向 | Java 核心与网页界面，采用 Electron、React、TypeScript、Java 21 和 Spring Boot |
| 模型来源 | 以外部 API 和现有编程工具为主，同时支持自研 Agent 运行时 |
| 协作模式 | 主副 Agent、圆桌讨论、流水线；按任务选择并支持阶段组合 |
| 调度目标 | 先满足质量与风险要求，再优化整体交付时间、返工和费用 |
| 记忆策略 | 自动提炼、分级生效；项目知识隔离，确认后的个人偏好跨项目共享 |
| 授权资源 | 用户预先授权的 API 密钥及独立登录配置；在项目允许的候选池内路由 |
| 默认自主程度 | 确认计划后，在既定权限、预算和修改范围内自动执行 |
| 交付边界 | 自动实现、验证、审查和有限修复；最终由用户验收，默认不自动提交、推送或发布 |

### 1.2 第一版边界和后续扩展

基础版本处理用户信任的本地 Git 项目。开发任务使用独立任务工作目录，所有修改和验证有明确版本。三端是正式发布验收目标，不能以一端验证代替三端验证。

云端多人组织、远程执行集群、插件市场、托管计费和自部署模型推理优化不列入第一版交付。接口保留扩展空间；外部 API 的应用效率优化列入核心建设。

支持未提交修改共存是明确的后续必做能力。早期验证阶段可以要求工作区干净；面向日常使用的版本必须支持选择带入已有改动，并保护用户原工作区及暂存状态。

跨仓库工作集和验收后的任务重开列入 M4，在单仓库闭环稳定后交付；本地多仓库协作不要求先建设云端多人组织。

## 2 用户流程与工作台界面

### 2.1 统一研发流程

接收需求 → 任务准入 → 理解项目 → 分析与澄清 → 制定完成约定 → 选择协作模式 → 检查计划 → 确认执行 → 准备环境 → 分配执行者和工具 → 协作执行 → 整合验证 → 独立审查 → 修复复审 → 人工验收 → 沉淀经验。

简单任务允许缩短开发分工，由主 Agent 独立实现并自检；仍执行完成约定中的必要验证与独立审查。高风险任务增加相应验收要求。每个阶段保留输入、输出、责任者、状态和失败恢复位置。

### 2.2 主要界面

- 项目首页：环境状态、项目地图、最近任务、知识更新和已知阻塞。
- 任务工作台：目标、完成约定、协作计划、依赖、当前模式与阶段。
- 执行详情：Agent 分工、模型与路由选择理由、工具活动、时间线和资源消耗。
- 上下文与记忆：本次注入内容、来源、版本、有效性、索引覆盖与检索诊断及编辑纠错入口。
- 成果与审查：代码差异、验证证据、问题清单、修复记录和验收操作。
- 需要我处理：合并展示需求澄清、架构取舍、权限变化、未解决问题和待验收成果。
- 资源与设置：运行器、模型、账号、API、MCP、预算、权限、自主程度、角色模板与本机资源限制。

每个需要用户决定的事项给出背景、证据、推荐方案与影响。普通进度进入看板；通知默认用于完成、故障和必须处理的事项。

### 2.3 人工接手与目标变更

用户可以暂停、取消、补充要求、锁定模式或执行者。人工接手前停止平台管理的相关写入，提供代码现场、执行记录、未完成事项和下一步建议。

目标变化时先分析影响，显示需要重做的任务、失效证据及仍可复用的成果。范围内调整更新计划版本；扩大权限、预算或产生新的重大取舍时进入待办。只重做受影响部分。

### 2.4 验收后的任务重开（M4）

用户报告遗漏或回归时，创建关联原任务的新处理记录，继承原需求、决策和相关经验引用。历史验收、代码和证据保持不变，新记录有自己的当前基线、完成约定与验收结果。

基于当前代码重新分析影响，只恢复必要阶段。修复或撤回前检查此后新增的修改，不直接恢复旧快照覆盖新工作；新证据推翻的经验进入复核状态。

## 3 任务准入与可执行计划

### 3.1 任务准入和停止投入

派发前查询重复任务、已有成果、相关分支和前置条件。发现重复时建议复用或合并；发现目标冲突时先解决冲突；必要条件缺失时明确等待原因。

执行中遇到目标失效、关键前提被推翻、已有方案不再适用，或连续尝试没有产生新证据时，进入重新决策。剩余预算充足并不自动证明继续尝试有价值。

无法完成的任务也要交付已确认事实、失败尝试、未解决问题、现有成果和恢复条件。任务可以以部分成果或已解释的阻塞结束，不能伪装成验收成功。

### 3.2 任务画像与完成约定

分析阶段只读查询项目与相关资料，提取任务类型、技术栈、修改范围、上下文需求、依赖、未知信息、风险、所需能力及工具。

完成约定包含目标用户行为、交付物、允许修改范围、必须遵守的规则、验收证据、必要测试和升级给用户的条件。关键歧义先澄清，其他假设显式记录。

完成约定与验收基线独立保存并版本化。开发执行者可以提出修改建议，不能单方面减少必要检查或降低验收标准。

### 3.3 计划检查器

负责人生成结构化依赖图后，由 Java 核心检查计划是否可执行：

- 图中没有循环依赖，前置条件有明确提供方。
- 每个阶段有责任角色、输入、输出、验收条件与终止条件。
- 上游成果能够满足下游输入，版本与类型相符。
- 所需运行器、工具、授权、环境和容量实际存在。
- 同一关键接口、结构或资源的并行修改已经协调。
- 副任务数量、递归深度、重试、修复和模式切换有界。

检查器只对结构和已知约束给出确定结论，不宣称能证明业务方案正确。失败项交回负责人修订；无法修订的事项进入用户待办。

## 4 三种协作模式与阶段切换

### 4.1 模式职责

| 模式 | 适用场景 | 执行协议 | 主要产物 |
| --- | --- | --- | --- |
| 主 Agent 与副 Agent | 未知多、需要动态探索或调整分工 | 主 Agent 规划协调，副 Agent 调查或实现有边界的子任务 | 发现、任务成果、进度与交接记录 |
| 多 Agent 圆桌 | 架构取舍、方案比较、相互冲突的解释 | 独立分析，交叉质疑与取证，汇总决策 | 方案、证据、取舍、分歧和待验证项 |
| 多 Agent 流水线 | 阶段稳定、输入输出与门禁明确 | 按交接契约推进，可在依赖允许时分支并行 | 分阶段成果及验证证据 |

### 4.2 自动选择规则

优先判断未知是什么：需求缺失先澄清；缺少事实先调查或实验；存在需要权衡的方案进入圆桌；阶段和交付明确则进入流水线；其他需要动态调整的任务采用主副模式。

模式选择同时考虑依赖紧密程度、可并行范围、风险、预计协调开销和预算。简单任务允许主 Agent 独立执行；高风险意味着更强的验证要求，不意味着必须增加讨论人数。

第一版采用可解释规则，显示选择依据并允许用户覆盖。后续根据任务类别和实测表现校准，不直接用总体成功率自动替换策略。

### 4.3 圆桌协议

默认三个专业角色，由任务需求选择实现、架构、测试等视角。协议为一轮独立提案、一轮交叉质疑、一次汇总；执行并发仍受全局限制。

独立提案在提交前互不可见。讨论必须区分事实、假设和偏好；必要时提出查询或隔离实验。汇总保留推荐方案、证据、反证条件、异议和未知项。缺少证据或涉及用户偏好时转为待办，一致意见不能代替验证。

圆桌默认具备查询与隔离实验权限，不直接修改交付工作目录。达到轮次或预算上限后输出当前结论并结束。

### 4.4 流水线和主副协议

流水线按完成约定推进：需求分析、方案、实现、测试、审查、交付。各阶段明确失败返回点；不能因为某个 Agent 声称完成就跳过门禁。

主副模式中的子任务由调度器创建，权限与预算继承根任务约束。负责人负责整合信息和调整计划，不能代替最终独立验收。主 Agent 故障也使用相同检查点恢复流程。

### 4.5 阶段组合与切换

允许圆桌确定方案、主副调查拆分、流水线实现验证的组合。调查完成后可转流水线；实现发现重大取舍时暂停相关部分进入圆桌；流水线发现未知问题时插入调查阶段。

切换在明确的阶段边界或异常恢复时进行，保存原因、计划版本、已完成成果、待办和上下文清单。重新检查依赖及权限，标记受影响旧证据。默认每个阶段自动改变协作策略最多两次，超过后进入重新决策，防止反复切换。

### 4.6 Agent 职责模板

角色使用版本化职责模板，记录职责、适用任务、项目规则、所需工具能力、默认模型偏好与备选组合、输入输出格式、自检要求及升级给用户的条件。职责与具体模型分开，更换模型后继续遵守原有交付要求。

首个日常使用版本提供内置模板及本地编辑、导入和导出，能力在 M2 交付。职责模板描述单个执行者如何工作，流程模板描述多个阶段如何衔接。模板只能声明能力需求，实际权限仍取任务授权与执行者能力的交集，导入不会增加权限。

## 5 项目地图与持续记忆

### 5.1 项目地图

建立需求、功能、模块、接口、文件、测试、历史问题和架构决策之间的关联。关系附来源、代码版本与确认状态。以代码索引、引用关系、项目文档和用户确认的模块地图为起点。

代码变化后识别可能受影响的测试、文档、记忆和任务，提示复核。静态关系分析用于辅助判断，不承诺识别全部业务影响。

### 5.2 分层记忆和知识类型

| 信息层 | 保存内容 | 默认范围 |
| --- | --- | --- |
| 用户偏好 | 用户确认的通用风格与习惯 | 用户全部项目 |
| 项目知识 | 模块、接口、约定、架构决策和环境 | 当前项目 |
| 任务状态 | 目标、发现、变更、失败尝试、阻塞和待办 | 当前任务协作者 |
| 开发经验 | 已验证原因、有效修复和验证方法 | 当前项目 |
| 原始记录 | 会话、工具调用、日志和成果 | 按来源及权限追溯 |

知识类型区分事实、决策、经验、限制、假设和失败记录。临时发现立即进入共享区；代码观察和测试观察按证据覆盖范围生效；审查与用户验收后沉淀经验。重要规则及跨项目偏好由用户确认。

### 5.3 来源链与独立证据

每条结论记录原始证据、引用链、适用条件、文件、分支、代码版本和状态。多次转述同一来源不增加独立证据数量，不能通过 Agent 相互引用升级可信度。

直接观察、测试结果、推断和用户决策分别存储。重大假设记录可推翻它的观察条件。圆桌和审查能够追溯到原始证据，而非只读取其他 Agent 的摘要。

### 5.4 记忆治理

支持编辑、核验、停用、删除、冲突标记和修订历史。相关文件变化后将依赖记忆标记待核验；错误结论被推翻时，关联摘要、经验和计划一并复核。

删除与撤权同时影响检索索引、缓存、摘要和运行中的上下文清单。关键纠错需要重组上下文；必要时停止旧会话，通过新会话接续。外部服务已收到的数据不能由本地删除动作保证撤回，按实际供应商能力处理并记录边界。

当前明确要求和适用项目规则优先于历史记忆。跨项目知识默认隔离，缓存和导出也遵循相同范围。

### 5.5 检索质量与索引诊断

组合代码符号、引用关系和关键词检索；配置了项目允许使用的嵌入服务后，再增加语义检索。语义能力不可用时可以回到符号和关键词检索，但必须展示能力变化及覆盖限制。

索引状态记录覆盖范围、对应代码版本、更新时间、失败文件和待更新模块。索引未完成或版本落后时，结果带覆盖说明，不能把未检索到当作资料不存在。

建立项目专属检索用例，覆盖业务表述与代码命名不同、关键架构决策及过期资料等情况。评估关键资料召回、来源正确性、过期内容命中和查询耗时，检索失败与模型推理失败分别归因。

## 6 一致上下文与协作信息交换

### 6.1 执行上下文清单

每次执行固定需求版本、代码基线、规则版本、工具定义版本和关键证据版本。上下文服务生成可追溯清单，避免混合不同分支的接口、实现和测试结果。

新增事件进入待处理更新区，在工具调用或阶段交接边界评估后应用。普通更新按需注入；撤权等必须立即生效的变更阻止后续调用并触发受控停止。

### 6.2 按任务组装与订阅

上下文包含必要规则、当前目标、相关代码、有效结论、执行进度和详细记录入口。去重和压缩时保留证据引用、未解决问题和失败原因。角色可见范围由任务需要决定。

Agent 按接口变化、依赖完成、测试结果等事件订阅，普通信息不广播给全部执行者。来源、任务身份和分支信息随消息传递。

用户可以查看本次使用哪些资料、为什么提供、哪些资料已过时。上下文预算由执行组合配置，超过预算时先删无关和重复信息，再提炼历史，必要证据通过引用保留。

查询诊断记录查询条件、索引版本与覆盖状态、候选资料、最终选入上下文的内容及选择原因，并保留来源入口。用户可以标记无关资料和缺失参考；反馈形成可审核的检索改进数据，不直接改写事实、提高证据等级或扩大资料可见范围。

### 6.3 委派权限与交接包

委派携带根任务、子任务、授权版本、项目范围和目的。接收者实际权限为自身能力、任务授权和委派范围的交集。外部资料经其他 Agent 转述后仍保留原来源，不能获得更高信任或权限。

接续包提供完成约定、适用规则、目标版本、已有修改、已执行操作、失败尝试、未知副作用、待办和下一步。跨引擎接管使用显式资料和成果，不假设可以迁移模型内部状态。

## 7 模型能力与全局资源调度

### 7.1 能力档案和路由选择

能力档案以模型版本、Agent 引擎和工具配置为单位，按任务类别、技术栈及项目记录表现。官方资料与用户配置提供初始参考，标明未经本项目验证。

执行路由由引擎、模型、供应商、API 地址和授权配置组成。先满足硬锁定，再过滤工具能力、权限、数据发送范围、预算、健康状态和容量，再满足任务质量与风险要求，最后比较预计整体耗时、返工、费用和切换成本。

可配置推理投入的运行器按任务分配投入；不支持的能力明确显示。复杂任务允许直接使用强能力组合，不固定采用先低成本失败再升级的流程。

“优先使用”是可降级偏好，“锁定”是必须满足的约束。用户可分别锁定模型、引擎、供应商或授权配置；自动故障转移只能改变未锁定维度，且仍满足数据范围、能力和预算限制。没有符合条件的候选时保存现场，显示具体阻塞原因并等待用户处理；解除锁定必须由用户操作。

路由读取任务固定版本的职责模板，将能力需求与模型偏好分别处理。备选模型只能更换执行组合，不能改变职责、交付标准或任务授权。

### 7.2 学习和归因

实际测试、用户验收和人工纠正用于更新档案。环境失败、工具故障、上下文缺失和模型能力问题分开统计。记录任务难度、运行配置和人工救援，不根据总体成功率直接排名。

模型版本变化建立新档案；样本不足时使用配置优先级和不确定标记。默认不额外启动付费能力评测。每次路由选择显示依据，用户可锁定执行者。

### 7.3 全局调度与公平性

所有项目、协作模式、子 Agent 和实验共用全局资源约束。分别统计逻辑角色、存活进程、模型在途请求、工具容量及排他写入资源；端口、数据库和测试环境也单独声明容量或排他使用要求。角色数、进程数不等于正在调用模型的请求数。

请求次数、累计执行时间、失败尝试与接管次数同时累计到根任务。重规划、新建替代子任务、复用角色和模式切换不重置根计数器，根限制优先于局部限制。

先满足依赖，再结合用户优先级、关键路径和等待时间安排。等待时间用于避免低优先级长期饥饿。副任务创建经调度器审批，检查角色数量、递归深度与根预算；这里的审批由程序执行，不逐次打断用户。

相同版本、权限和语义的只读调查允许合并执行并共享结果；独立审查的判断不合并。成本计入重试、接管、上下文重建和失败尝试。

### 7.4 等待释放与资源互锁

等待依赖、其他圆桌提案或人工输入时，释放已经结束或可确认挂起的模型请求容量。工具仍在运行时保留工具容量和必要写入保护；释放模型名额不等于转让工作目录写入归属，也不代表仍在途的模型请求已停止计费。

原生 CLI 无法确认挂起时，启动前为副任务预留可执行容量，或将父任务拆成可确认停止、保存和恢复的阶段。不能只修改平台状态就宣称资源已释放。全局模型执行容量默认二，两个父任务同时等待副任务以及三个圆桌角色分轮执行，都必须在该限制下推进；能力不足的适配器组合在计划检查时拒绝或改用可执行方案。

每阶段先声明所需资源，按固定顺序申请；无法完成申请时释放临时预留并重新排队，避免占着数据库等模型、同时另一任务占着模型等数据库。跨阶段必须保留的写入保护单独声明，依赖任务如需该资源，应在可确认停止的边界交接或重新安排阶段，不能让父任务持锁等待需要同一锁的副任务。

运行期维护资源等待关系并检查循环；发现互锁时撤销可安全释放的临时预留，重排或停止相关阶段。不能释放的资源明确报告，未经停止确认不强行转让。等待期间收到取消后删除待派发申请，释放临时预留，对仍在途操作按第 9 章核对。

### 7.5 授权池与验证预算预留

使用预先授权的 API 密钥和独立登录配置。额度按实际账号、组织或项目归组，不能将同组多个密钥视为独立容量。登录隔离不可靠的配置不参加自动账号切换。

可估算请求在派发前预留预算，结算后调整，统计在途与已完成消耗。缺少准确价格或用量时显示软预算，并用调用次数、时长与并发约束。未知费用不能视为零，不承诺不透明运行器的实际费用绝对封顶。

候选池包含项目允许发送数据的供应商。未知价格路由默认不参加自动切换，用户可事先启用。根任务到达限制后不再启动新调用，已在途操作继续核对和受控停止。

根预算包含分析、任务分类、规划、路由、记忆整理、开发、验证、独立审查、交付整理、重试及接管；平台自身的模型调用也必须登记。项目级后台工作使用显式的维护预算，不能借转移任务归属绕过根限制。

依据完成约定，为剩余必要验证、一次独立审查及交付整理估算并预留资源。预留属于根预算，不增加总额度；同时统计已消耗、在途承诺、预留和开发可用余额，避免重复扣算。预留随剩余工作和价格信息更新，费用不透明时以调用次数和时长提供软预算，由用户查看和调整，不能承诺必定足够完成。

普通开发不得使用验证预留。开发可用余额不足时停止新增开发，转入可负担的必要验证、范围调整或部分交付处理；必要修复和复审重新估算资源。无法完成必要检查时标记未验证，不降低验收标准；总预算耗尽后不能以验证预留为由启动额外调用。

## 8 MCP 与工具执行管理

### 8.1 双向 MCP 与内置工具

作为客户端支持本地 stdio 和远程 Streamable HTTP，管理连接、能力发现、授权及健康状态。作为服务端提供项目记忆、上下文、任务状态、共享发现和成果查询。

内置文件、代码搜索、命令、Git、构建、测试和浏览器验证能力。工具资源、可调用动作和提示模板分别管理，按服务与客户端实际协商能力启用。

### 8.2 工具身份与变更

工具绑定包含服务身份、工具名称和定义版本。任务固定工具清单，解决不同服务同名工具以及运行中定义变化问题。

重连或工具变化通知后比较参数、权限和副作用描述，使相关缓存失效，重新核验受影响任务。工具声明只读或幂等仅为参考，实际约束由平台策略和已验证适配决定。

### 8.3 统一工具层

工具档案包含适用场景、前置条件、参数与输出结构、权限、副作用、超时、耗时、失败记录和替代工具。按任务发现和加载必要工具。

统一校验参数、限定项目与目录范围、执行取消和超时、脱敏记录输入与结果。大结果保存为成果，提供摘要及引用。外部内容作为数据，不能修改平台规则、调用范围或授权。

原生 Agent 工具通过适配器申报实际可观测、可控制能力。需要强制控制而适配器无法提供时，不将对应任务交给该运行器。远程 MCP 独立处理授权，不无条件透传其他服务凭据。

### 8.4 服务依赖与局部降级

计划区分必要能力与可选服务。可选 MCP 离线时暂停实际依赖它的任务，其他独立任务继续；替代工具必须满足原权限、数据范围和交付要求。必要能力缺失且无合格替代时保留成果并明确阻塞，不能删除相应验收门禁。

服务恢复后重新发现并核验身份、工具定义、授权与健康状态，核对中断操作再恢复派发。能力变化及其影响在任务工作台展示。

## 9 持久执行与自动恢复

### 9.1 任务状态与持久派发

任务状态覆盖未开始、待派发、运行中、等待输入、等待依赖、等待资源、结果未知、恢复中、取消中、已取消、失败、待验收和已完成。模式和角色使用同一执行状态体系。等待状态与实际资源占用分别记录，按第 7.4 节确认后释放容量，不能仅凭状态文字判断进程或工具已经停止。

执行状态与业务结果分开记录。结束的任务可标记成功、部分交付、失败或取消；只有满足验收要求并被接受的完整交付计为成功。阻塞可继续等待，或由用户选择以部分交付结束，不提高成功率统计。

任务状态变化、执行尝试和待派发动作在同一数据库事务内保存。派发器读取持久队列，使用唯一编号去重。进程启动采用单实例执行包装器和启动回执，重启先核验实际进程与未完成动作，再开放调度。

事件按编号去重并记录顺序。执行尝试有独立写入归属；不能因心跳失效就认定旧进程已停止。工具网关拒绝旧归属调用；首版直接文件写入运行器必须确认旧执行及子进程停止后交接，不能仅更换工作目录便继续。能够证明访问隔离的并存恢复属于后续适配能力，不能代替首版停止确认要求。

### 9.2 副作用操作账本

工具调用前记录操作编号、意图、参数摘要、授权和目标资源。操作状态为准备、已发送、已确认、结果未知及已核对，补偿动作独立记录。

工具支持幂等键时重试沿用同一标识；不支持时先查询远端状态；无法确认则暂停该操作并报告。取消请求不代表远端效果已经撤销。平台不承诺任意外部工具都具备恰好一次执行保证。

### 9.3 故障分类与恢复

| 类型 | 默认处理 |
| --- | --- |
| 网络或临时服务错误 | 有限退避重试，结合服务端提示，再选健康路由 |
| 限流或额度耗尽 | 对实际额度组冷却，按重置时间恢复或选独立可用资源 |
| 鉴权或权限错误 | 停用受影响凭据或能力，等待修正 |
| 请求参数或上下文错误 | 修正请求或重新组装上下文 |
| 环境故障 | 核验和修复环境，避免直接归因于模型 |
| 无进展或方案失效 | 检查证据，重新规划，再决定升级、实验或交接 |
| 等待用户或正常长工具 | 保持等待，使用对应状态和工具超时 |

主任务、子任务、SDK 和工具遵循唯一重试责任层；无法禁用的内部重试由适配器声明并计入限制。默认不同时叠加多层未知重试。

### 9.4 检查点和接管

在工具完成、代码阶段完成及交接边界保存检查点，持续保存事件。检查点包含文件新增、修改、删除、代码版本、执行记录、未知操作、成果、任务状态和会话标识。

接管顺序为中断旧执行、确认停止、保存最终现场、选择候选、恢复上下文、核验已有成果、继续。中断超时后可终止平台管理的进程树；无法确认停止则禁止对同一现场接管写入。

兼容的原生会话可恢复；跨账号、跨模型或引擎不兼容时使用新会话和接续包。旧事件不能覆盖新状态，已验证成果不因局部重试被清除。

### 9.5 取消传播

取消沿根任务传播到副 Agent、工具和待派发队列，禁止新增调用。状态区分已请求、正在停止、已停止和仍有未确认操作。残留进程、远端操作和费用都记录在交付说明中，不能仅凭界面取消就释放同一写入资源。

基础根任务取消、预算及资源约束从 M1 生效。M2 扩展的全部副任务、圆桌和流水线都受同一约束，M3 补全跨账号、跨引擎及长期恢复场景。

### 9.6 功能降级与恢复边界

| 故障 | 允许的处理 | 恢复前核验 |
| --- | --- | --- |
| 语义检索不可用 | 使用符号与关键词检索，显示能力及覆盖变化 | 服务配置、数据授权、索引版本 |
| 可选 MCP 离线 | 暂停依赖任务，独立任务继续 | 服务身份、工具版本、授权和未完成操作 |
| 单一供应商不可用 | 在批准候选池及锁定约束内恢复 | 健康、额度、能力、预算和旧执行停止情况 |
| 全部模型不可用 | 保留已有代码、成果和记录的查看、导出及人工接手能力 | 可用路由及人工接手期间的代码变化 |
| 持久状态或授权校验失败 | 停止新增自动修改，受控停止在途执行，尽力保存可恢复现场 | 存储、授权、一致性及结果未知操作 |

降级不能解除硬锁定、扩大授权或省略必要门禁。存储不可写时不宣称检查点已成功保存；尚无法确认的执行保留未知状态与写入保护。恢复后按实际能力、版本和未完成操作重新核验，通过后才恢复派发。

## 10 工作环境与成果整合

### 10.1 项目环境档案

记录运行时、依赖、启动和验证命令、测试数据、数据库、外部服务替代配置及已知问题。执行前检查环境，普通缺失按项目授权修复，新增权限或不可逆变化进入待办。

并行任务使用独立 Git 工作目录及临时资源。仅工作目录隔离不被视为操作系统权限隔离；执行边界按工具和运行器实际能力实现并明确展示。

修改前在隔离基线和匹配环境中运行任务相关的必要检查，记录代码、配置、依赖、测试数据及原始结果，作为第 11.4 节的失败对照。无法执行基线时标记缺失及原因；测试环境不可比时明确归因限制。

### 10.2 与未提交修改共存

早期闭环要求干净工作区。日常使用阶段增加原提交、暂存、未暂存和未跟踪文件清单，用户可选择带入本次任务的改动，建立独立快照，保留原目录和暂存状态。

忽略文件、凭据、依赖目录和大型文件不会盲目复制；运行所需配置以受控引用或环境档案提供。提供 IDE 选区、诊断、测试失败信息的接入入口。

### 10.3 语义冲突和整合队列

除文本冲突外，检查接口、数据库结构、配置、枚举及依赖关系的修改。任务声明读写范围与逻辑资源，涉及同一关键资源时提前协调或排序；分析仅作预警，不承诺发现所有业务冲突。

每仓库使用单一整合队列。每项在最新目标基线、已整合成果与本次成果组成的版本上验证。基线或成果变动使相关证据失效。

用户采纳前再次核验目标目录变化。支持按任务、文件和代码块采纳；产生新组合后重新验证必要条件。最终交付内容与最终测试及审查绑定的内容标识一致。

### 10.4 跨仓库工作集（M4）

一个工作集可以关联前端、后端、公共 SDK 等多个本地仓库，分别记录基线、权限、成果和接口依赖。跨项目关系和允许共享的资料显式配置，原有知识与授权隔离不因加入工作集而自动解除。

联合验证绑定整组仓库版本；任一相关版本变化时重新评估联合证据。各仓库仍使用自己的整合队列，界面同时展示仓库状态及整体交付状态。某个仓库失败时保留其他成果，明确联合交付尚未完成。

多个 Git 仓库不具备平台可假设的原子提交或采纳能力。计划明确采纳顺序、兼容条件、失败处理和部分完成状态，不能把部分仓库已采纳误报为整体成功。

## 11 验证审查与证据完整性

### 11.1 分层质量门禁

| 层次 | 验证目标 |
| --- | --- |
| 静态检查 | 语法、类型、格式与明显错误 |
| 自动测试 | 正常行为、边界与回归 |
| 集成验证 | 接口、数据库和模块配合 |
| 实际操作 | 页面、交互与用户流程 |
| 独立审查 | 需求覆盖、正确性、兼容性、安全和遗漏风险 |

编辑后提前做轻量检查，子任务完成做相关测试，整合后运行规定验证。增量检查用于快速反馈，不取消完成约定中的必要门禁。

按第 7.5 节为剩余必要检查、一次独立审查和交付整理预留根预算。开发接近可用额度时优先完成可验证成果；必要检查无法负担时保留未验证状态，不以预算不足替代验收证据。

### 11.2 独立审查与修复

审查者使用独立会话和审查工作目录，首先阅读需求、完成约定、最终差异和验证记录，再查看开发者说明。审查按风险选取角色和能力，不能只依据实现者自报完成。

问题记录位置、原因、证据、影响、建议和验证方式，区分阻断问题与改进建议。阻断问题自动交回开发者修复，最多两轮，每轮重新验证和复审；达到上限仍未解决时保留成果与问题清单。

### 11.3 验收依据完整性

验收基线、平台触发的检查和执行结果独立保存。测试、断言、构建脚本和检查配置的变更单独列出供审查，防止通过删除检查制造成功。

每条验证证据绑定代码与环境标识、命令、执行器、时间、退出状态和报告。未执行标为未验证，无法判断标为未知。开发执行者不能覆盖验收记录或将失败改为通过。

用户验收与机器验证是独立状态。用户接受有遗留问题的成果时，保留事实与风险说明，不把未验证状态改写为测试通过。

验收后重开的新处理记录关联原验收及证据，新增修复和检查绑定当前版本；不覆盖旧失败、旧通过或原用户决定。相关经验的复核与修复结果一同记录。

### 11.4 基线失败与不稳定测试归因

将修改后的失败与第 10.1 节保存的相关基线检查对照，区分新增回归、原有问题、环境问题、疑似不稳定及无法归因。分类附代码与环境差异、执行记录和判断依据，证据不足时保持未知。

疑似不稳定测试在同一代码版本和可比环境下最多追加两次复现，保留首次及每次追加结果，不通过反复运行直到成功覆盖失败。复现次数与路由重试、修复复审分别计数，全部消耗计入根预算。偶然成功不能使不稳定检查自动变为可靠通过。

原有失败不自动扩大当前任务范围；若影响必要验收，报告影响并由用户确认处理范围或调整完成约定，保留原记录。无法执行基线时说明归因受限，不能据此宣称本次修改没有引入问题。

## 12 模型与整体研发效率优化

### 12.1 效率账本

逐任务记录排队、上下文准备、模型响应、工具执行、交接、验证、返工和人工介入。区分首次响应与总完成时间，以及关键路径耗时与并行累计耗时。

记录输入输出 Token、缓存用量、请求次数、实际或估算费用、重复读取、无效重试和最终质量。运行器未提供的数据明确为未知。

分析、规划、路由判断、记忆整理和评估等平台开销单独列项，并按实际所属根任务或明确的维护预算入账。比较策略时计入全部开销，不能只展示开发 Agent 的调用费用。

### 12.2 上下文和缓存

按任务组装上下文，去重历史，定位相关代码，筛选日志并保留完整来源。接续摘要必须保留失败原因、未解决事项和证据入口。

| 缓存 | 保存内容 | 有效性条件 |
| --- | --- | --- |
| 提示前缀 | 稳定规则、工具定义和固定资料 | 按供应商与运行器能力实现，记录配置版本 |
| 检索 | 文件定位、引用关系和文档检索 | 代码、索引、查询和权限版本一致 |
| 只读工具结果 | 可复用的查询或计算结果 | 环境、参数、身份、范围和有效期满足约束 |

写入操作不做结果重放。测试缓存只有在完整相关输入仍有效时复用，必要验收按契约执行。独立账号、项目与授权之间不错误共享缓存。原生工具自身管理的缓存只使用可观测能力，不宣称平台可以强制控制。

### 12.3 减少往返和优化关键路径

参数检查、版本比较、结果解析、已知错误分类、日志筛选和统计由确定性程序完成。独立查询批量执行，大结果先在工具侧处理，模型专注理解、规划、判断和生成。

合并同语义、版本及权限的重复只读调查。优先推进阻塞后续工作的任务，分别管理工具、模型和环境瓶颈。模型及推理投入按任务选择，计入缓存冷启动和接管成本。

简单任务优先采用已经验证的规则与模板，避免为分类和路由反复调用模型。非必要记忆整理及后台评估可以延后；与当前验收直接相关的证据保存不能延后到失去可恢复性。

### 12.4 评测和归因校正

固定代码、环境、需求、验收与知识快照，防止新策略使用基线任务沉淀的答案。按任务类型和难度配对比较，分别统计冷缓存与热缓存，初始每项每种配置重复三次，后续按波动增加样本。

每轮重置规定的知识和缓存状态；热缓存使用一致的预热流程，并将预热开销单列。付费评测启动前展示任务数、配置数、重复次数、总运行数量与预算范围，按已配置授权执行。十二个任务、四种配置、每种三次即至少一百四十四次运行；增加冷热缓存组合或复现时重新计算，不以少量请求的价格代表整轮费用。

失败、放弃、人工救援、重试和接管全部计入。环境、工具、模型、上下文和计划失败分别归因。报告分布与样本不足，不依据少量任务断言某模型或模式普遍更优。

检索评测单列关键资料召回、来源正确性、过期内容命中和查询耗时，结合索引覆盖及用户反馈判断问题发生在检索还是后续推理。测试失败使用第 11.4 节的基线对照，不把原有失败或环境变化直接归为模型能力不足。

每次主要调整一类策略，通过质量门槛后再评估时间、费用和人工负担。策略版本可回退，默认不开展未经配置的额外付费实验。

### 12.5 本机性能与交互响应

前台任务优先于后台索引、非必要记忆整理和评估，后台工作支持暂停与恢复。记录本机 CPU、内存、进程数量、磁盘和工具资源使用，按可配置并发、容量和队列限制调度；阈值通过目标设备测量确定，不以模型并发限制代替本机资源治理。

日志批量显示，长列表按需渲染，大文件、巨大差异和大量工具结果分段读取。界面订阅使用有界缓冲与事件游标，慢界面从持久记录续读；重复进度刷新允许合并，核心持久事件保持完整。界面刷新不能阻塞执行核心，暂停、取消和人工接手命令优先处理。

在声明的设备、日志速率、任务并发和运行时长下验证响应时间、内存变化与队列积压，将测试负载和目标值写入实施验收配置。测试重点包括索引与测试同时运行、大量输出、慢速界面和长时间运行后仍可及时请求暂停及取消；界面响应与执行实际停止分别计时。

## 13 长期运行与数据生命周期

### 13.1 桌面生命周期

关闭窗口默认进入托盘继续运行，明确退出时受控停止并保存现场；用户可修改行为，界面显示后台运行状态。系统不支持相应后台能力时使用实际可用行为并提示。

锁屏不自动取消任务。休眠、断网或网络切换后先核验进程、连接、授权、工具和任务状态，再调度；休眠时长不直接计入卡死判断。核心异常退出后使用持久化恢复流程。

按第 9.6 节展示当前降级范围和恢复条件。全部模型不可用时仍能查看、导出已保存成果并人工接手；存储或授权校验失败时只提供实际可保证的读取与恢复入口，不继续新增自动修改。

### 13.2 一致存储与清理

成果采用内容标识和引用关系保存，文件持久化完成后再提交数据库可见引用。日志、证据、补丁、检查点与记忆的依赖可查询。失败写入不能制造可见但不存在的成果。

运行中任务、未知副作用、未验收成果和有效记忆引用的证据不自动清理。保留策略分为临时产物、任务档案、验证证据和长期知识，用户可以调整。

备份包含数据库、成果及配置的相容快照，凭据独立处理、不默认导出。恢复后检查所有有效引用。磁盘不足时停止启动新任务并优先保存已有现场。

### 13.3 可携带交付包

验收时生成可独立读取的任务包，包含代码基线与补丁、需求、计划和决策、验证命令及结果、遗留问题、记忆来源索引和带版本的机器可读清单。

交付包支持换工具、换设备与人工交接，排除凭据及不在导出范围内的资料。内部检查点用于恢复平台执行，交付包用于恢复研发工作，两者有不同的完整性检查。

### 13.4 长期性能与订阅恢复

持续监测执行、索引和界面订阅的队列积压。资源紧张时先暂停可延后的后台工作、限制新增派发，并保留控制命令处理能力；不能通过丢弃必要持久事件伪装恢复。

界面重连或从休眠恢复后按游标续读。游标对应事件已按保留策略清理时，读取一致状态快照并从新的事件位置继续，明确显示恢复范围。长时间运行验收记录资源趋势、积压是否收敛及暂停取消响应，具体负载遵循第 12.5 节。

## 14 自主程度与持续改进

### 14.1 渐进授权

提供辅助分析、确认后执行和授权范围内持续执行三级模式。授权按项目、任务类型、动作范围、数据范围和资源预算配置，可撤销。

成功记录可以触发授权调整建议，但权限扩大必须由用户确认。首次接入优先完成低影响、可验证任务，导入现有规则和环境，逐步建立信任。

### 14.2 最小实验选择

面对未知，平台在查询、澄清、实验、讨论和直接实现之间选择最能获得必要证据的动作。假设可用最小复现验证，兼容性可用契约测试验证，性能取舍可用小规模基准验证。

每个实验有问题、预期观察、反证条件、预算、隔离环境和结束条件；结果进入证据库。超出授权或产生额外成本时遵循项目策略。实验结束后只将有依据的结论交给圆桌或计划器。

### 14.3 模板 维护与版本化

从已验收任务提炼流程模板，保留适用条件、步骤、工具、验证要求与失败经验。改进流程为候选提案、历史评测、用户批准、发布新版本和可回退。

任务固定策略、提示模板、工具协议与验收版本。更新不静默改变进行中的任务；迁移前保存检查点，无法兼容时完成旧任务或显式迁移。

职责模板使用独立的 AgentProfile 版本，任务固定启动时的版本。本地编辑或导入后先校验结构、能力需求和授权兼容性，在既定预算与权限内试运行，再发布可回退版本；更新不直接影响进行中的任务。流程模板可引用职责模板版本，但不能将所需工具声明当作工具授权。

后续从失败测试、日志和缺陷生成候选维护任务，更新文档、知识和项目地图，识别反复返工中的技术债。只有已授权任务类别自动执行，其他进入待办。

M4 的验收后重开沿用第 2.4 节的新处理记录，关联原任务、原验收及当前修复。被新证据推翻的经验暂停直接用于后续决策，复核结果形成新修订并传播到相关上下文，不重写历史证据。

调度沙盘使用合成事件和历史记录测试模式选择、资源竞争、计划缺陷与故障恢复，默认不调用付费模型。历史回放标记可重现逻辑、录制结果与无法精确重现的外部行为。

## 15 技术架构与接口边界

### 15.1 部署结构

Electron 负责桌面窗口和核心进程生命周期，React 与 TypeScript 提供界面。Java 21 与 Spring Boot 采用模块化单体实现规划、调度、知识、工具、验证和恢复。SQLite 保存结构化状态，Lucene 保存本地检索索引，文件系统保存不可变成果及日志。

桌面与核心通过仅监听本机的 HTTP 接口及 SSE 事件流通信，启动时生成访问令牌。安装包携带 Java 运行时。具体依赖版本在实施时验证兼容性并锁定，不在计划中承诺未来版本行为。

首批运行器为 Codex、Claude Code 和自研 Java Agent。优先使用官方可编程接口，并以接入探针验证实际能力。自研 Agent 首版提供项目文件、搜索、命令和工具循环，连接支持所需工具调用的 API；兼容性按真实端点测试。

### 15.2 模块接口

| 模块 | 主要接口与职责 |
| --- | --- |
| 项目与知识 | ProjectKnowledgeService、MemoryService、ContextService、RetrievalDiagnostics：索引、记忆治理、一致上下文及检索覆盖与反馈 |

### 15.3 核心数据契约

最小核心对象包括 Project、Task、CompletionContract、TaskProfile、CollaborationPlan、StageHandoff、ContextManifest、MemoryEntry、Evidence、RouteDecision、RunAttempt、ToolOperation、Checkpoint、Artifact、ReviewIssue 和 AcceptanceRecord。

1.1 补充职责配置 AgentProfile、预算策略 BudgetPolicy、路由约束 RouteConstraint、检索诊断 RetrievalDiagnostics 和能力健康 CapabilityHealth。资源记录分别表示容量类型、占用、临时预留、等待关系及排他写入归属，预算记录保留阶段消耗与验证预留，验证记录关联基线及每次复现证据。M4 增加 WorkspaceSet 的仓库版本集合和任务重开关联，保留历史 AcceptanceRecord。

统一关联项目、根任务、执行尝试、授权版本、输入基线与产物版本。状态变更有操作者、原因和事件编号。API 首版仅面向桌面及平台内部适配器，使用版本化对象；扩展接口不得绕过执行状态、工具授权或审查门禁。

### 15.4 开发约束

遵循用户既有 Java 注释规则：保留已有注释原文与格式，不为统一风格任意改写；新增文档注释采用标准多行形式，字段、方法和关键逻辑保留必要说明。

凭据存入系统凭据服务，服务不可用时只在会话内保存，不写普通配置或日志。系统权限、外部工具控制和操作幂等能力按适配器实际保证展示。

## 16 默认策略与配置

以下为可修改的起始值。任务开始时保存其策略快照，策略改变不悄然影响进行中的执行。

| 策略 | 起始默认值 |
| --- | --- |
| 全局模型执行容量 | 最多两个在途模型请求，每条路由并发一；角色、进程、工具和排他资源分别计数，按适配器真实能力核算 |
| 等待释放 | 只释放已结束或可确认挂起的模型请求容量；运行中的工具与必要写入保护继续保留；无法挂起时预留副任务容量或拆阶段 |
| 资源申请 | 阶段声明与固定顺序申请；不足则释放临时预留排队，跨阶段写入保护单列并检查等待环 |
| 角色上限 | 单根任务最多六个活动或待执行角色；角色可复用，超出时拆阶段 |
| 圆桌规模 | 三个角色，一轮独立提案、一轮质疑、一次汇总 |
| 策略切换 | 每阶段自动改变协作模式最多两次 |
| 路由重试 | 同路由最多重试两次，计入根任务限制 |
| 自动接管 | 每子任务最多自动切换三次 |
| 无进展处理 | 相同失败且无新证据三次，触发一次重新规划 |
| 活性检查 | 每五秒检查状态；无事件且无活动工具两分钟后疑似停滞，再核验一分钟 |
| 工具超时 | 默认十五分钟，按具体工具与任务覆盖 |
| 故障冷却 | 连续三次临时故障后冷却一分钟，再允许一次恢复探测；服务端提示优先 |
| 复审循环 | 最多两轮自动修复与复审 |
| 不稳定测试复现 | 在相同版本和可比环境最多追加两次；保留全部结果，与路由重试、复审分别计数并计入根预算 |
| 模型偏好与锁定 | 优先使用可降级；模型、引擎、供应商和授权配置的硬锁定只能由用户解除，无合格候选则保存现场并等待 |
| 验证预算预留 | 按剩余必要验证、一次独立审查和交付整理估算，计入根预算；普通开发不可占用，费用不透明时采用软预算 |
| 平台自身开销 | 分析、规划、路由、记忆整理和评估等纳入所属预算；非必要后台工作可以延后 |
| 预算与候选 | 开发额度不足先转入预留范围内的验证；根预算不足以完成必要工作、达到根限制或无合适候选时保存现场并等待用户处理 |
| 前后台优先级 | 前台执行及暂停取消优先；后台索引、整理与评估可暂停恢复，本机阈值按设备配置 |
| 界面订阅 | 有界缓冲、批量刷新和事件游标续读；完整持久事件不得因慢界面丢失 |
| 降级边界 | 可选服务故障仅阻塞依赖任务；存储或授权校验失败停止新增自动修改，必要验收及硬锁定保持有效 |
| 数据范围 | 项目知识隔离；确认后的个人偏好跨项目使用 |
| 自动执行 | 默认确认计划后执行；不自动提交、推送或发布 |
| 原始日志保留 | 已完成任务的可清理原始日志默认保留三十天；被证据引用者延长保留 |
| 临时文件保留 | 已验收且可重建的临时产物默认七天后进入可清理队列 |
| 空间阈值 | 可用空间低于磁盘容量百分之五或二 GB 任一条件时停止新任务并保存现场 |

用户可锁定更严格的策略。系统休眠、等待人工确认、已知长工具和运行器不可观测等待需要分别判断，不能只用无文字输出作卡死依据。

## 17 实施里程碑与交付门槛

### M0 架构与可执行性验证

完成接入探针、能力声明、任务及成果契约、持久状态与操作账本设计，验证三端进程管理和凭据服务。实现计划检查器、录制事件重放及最小故障注入脚手架。

验证角色、进程、模型请求、工具和排他资源的分别计数，确认原生 CLI 的挂起、停止及恢复边界；设计阶段资源申请、等待关系检查、根预算与预留、软偏好和硬锁定规则。

退出条件：能够说明每类运行器哪些能力可保证、哪些只能观察；崩溃边界不会被静默当作未执行；验收依据独立保存；资源互锁及无法满足的锁定约束能被识别，无法挂起的运行器有可执行调度方案。正式开发不以模拟能力宣称真实兼容。

### M1 可靠单任务闭环

交付项目导入、地图基础、完成约定、环境检查、单运行器执行、内置工具、记忆与一致上下文、检查点、代码差异、提前验证、独立审查和用户验收。加入效率账本、基本去重与检索缓存。

交付根任务取消、基础资源约束、根预算及验证预留，计入平台自身开销；实现硬锁定执行、基线失败归因和有限复现、关键词与符号检索的基础诊断、必要降级及界面有界缓冲与流量控制。

退出条件：可信项目的一次真实任务能完成、暂停、恢复和验收；对启动崩溃、工具结果未知、取消和测试配置修改有正确行为；开发不能占用验证预留、调度不能绕过锁定、偶然测试成功不能覆盖失败，存储或授权故障能停止新增自动修改。该阶段可以要求工作区干净。

### M2 三模式协作与混合接入

补齐 Codex、Claude Code、自研 Agent 接入，交付主副、圆桌、流水线、自动模式选择、成果交接、全局队列、能力匹配、共享订阅和双向 MCP。建立整合队列、语义冲突预警和版本门禁。

补齐多 Agent 等待释放、全局资源申请及运行期等待环检查，交付职责模板的内置版本、本地编辑与导入导出、固定版本和回退，以及 MCP 依赖降级。全部并行执行继承 M1 的根取消、预算及资源约束。

退出条件：三模式均通过真实任务验证，依赖失败返回正确位置，不发生越权委派、共识自证或旧版本成果错误复用；容量二时父副任务和三角色圆桌可以推进，资源反向申请与等待期间取消不会永久互锁，模板不能扩大授权。

### M3 长期自动化与日常使用

交付账号与 API 资源池、跨引擎接管、跨账号和跨引擎场景下的预算取消核对、桌面生命周期、完整备份恢复、磁盘治理、未提交修改共存、人工接手、目标变更、局部采纳和交付包。完成三端安装及运行验收。

完善长期性能治理、索引覆盖与运行状态诊断、慢界面续读、后台工作暂停恢复及完整故障恢复体验。基础停止和预算能力沿用 M1，不延后到本阶段才实现。

退出条件：长期运行、休眠恢复、网络切换、进程退出和未提交修改场景可解释且可恢复；最终采纳版本与验收证据相符；声明负载下大量日志与索引测试并行不会使控制命令失去响应，界面恢复能够续读完整有效状态。

### M4 效率与项目专属改进

完整交付三类缓存、工具批量执行、重复调查合并、推理投入、关键路径优化、对照评测和归因校正。扩展最小实验选择、流程模板、维护任务与项目专属能力档案。

交付符号、引用关系、关键词及可选语义能力的混合检索校准，扩展项目专属检索用例和反馈治理。增加跨仓库工作集、联合版本与部分交付状态，以及关联原验收的新任务重开记录与经验复核。

退出条件：新策略通过质量门槛，并在配对任务中展示可重复的时间、成本或人工负担改善；策略与模板可回退；多仓库部分失败不误报整体成功，验收后修复基于当前代码并保留原始证据。

M0 至 M3 构成首个可用于日常研发的发布范围。M4 分批迭代；基础观测和效率数据从 M1 开始采集，不能等最后才建设。

基本取消、根预算及资源约束从 M1 生效，M2 的全部并行能力在此基础上扩展；跨仓库工作集与验收后重开不列入 M0 至 M3 的完成门槛。

## 18 测试验收与运行保证

### 18.1 核心不变量

1. 同一交付现场同时只有一个有效写入归属；无法确认旧执行停止时不接管写入。
2. 结果未知不能自动视为未执行，外部副作用不盲目重放。
3. 最终交付内容与最终审查和必要验证绑定的版本一致。
4. 多次引用同一证据不会增加独立支持度。
5. Agent 委派、记忆或工具返回内容不能扩大用户授权。
6. 开发执行者不能单方面降低完成约定或覆盖验收证据。
7. 取消和预算约束覆盖整棵执行树，不能由副任务绕过。
8. 运行恢复、清理和备份不能留下无法解析的有效成果引用。
9. 等待释放必须符合实际执行状态，释放模型容量不能转让仍受保护的写入现场。
10. 硬锁定、授权和必要验收要求不被自动路由、模板或降级路径解除。
11. 验证预留属于根预算，普通开发及平台自身调用不能绕过其归属和限制。
12. 基线失败、追加复现和历史验收记录不能被后续偶然成功或任务重开覆盖。

| T35 | 多仓库联合任务中一个仓库失败或版本变化 | 验证绑定整组版本，保留各仓库成果并准确展示部分状态；不误报整体完成，不假设跨仓库原子采纳 |
| T36 | 验收后重开，当前代码已有后续修改 | 新处理记录关联原任务并保留历史验收与证据；基于当前版本修复，复核被推翻经验，不用旧快照覆盖新工作 |

### 18.3 效率验收

至少十二个代表任务覆盖续接、功能修改、疑难排错、主副、圆桌、流水线和模式组合，建立无记忆单 Agent、有记忆单 Agent、固定分工多 Agent、能力匹配多 Agent 四组比较。

主要指标为需求到验收总时间、人工介入、重复解释次数、首次验收通过率、每个验收任务总成本、交付后缺陷、接管耗时和首次接手到有效产出的时间。

同时报告自然交付时间、扣除等待用户后的执行时间和用户实际操作时间。等待用户按事件区间去重，只扣除确实使根任务无法推进的等待，不把仍有并行工作推进的时间整体扣除；用户操作时间单独测量，无法取得时标记未知。不能把全部等待时长当作人工劳动时长，也不能通过换统计口径宣称提速。

付费评测按第 12.4 节事先展示运行数量与预算范围，每轮重置规定的知识和缓存状态。报告包含平台自身开销、失败及复现，检索质量与代码交付质量分别列示。

试点目标为重复人工解释减少一半，接续任务中位耗时降低百分之三十，验收质量不下降。数值是待验证目标；样本与波动不足以支持结论时继续测量，并保留失败与未完成任务。
